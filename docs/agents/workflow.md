# Matt 工作流

## 接手与授权

主协调者从用户目标推进到验收和交付。先核对 Git 根、HEAD、目标分支、远端、未提交改动和现有 worktree。有相关工单或 PR 时，按[跟踪约定](issue-tracker.md)核对正文、依赖、审查与适用的 CI。跨到学校仓时重新检查这些边界。

主协调者在授权范围内决定研究、方案、规格、测试边界、拆票、派工、Git 操作与验收。能查证的事实自行查证。重大方案调整记录依据、备选和影响。只有关键事实无法合理查证、方向与用户明确要求冲突，或涉及尚未授权的重大外部影响时才确认。隔离局部阻塞，继续有条件的工作。

## 选路与调用

初次检查跟踪器、标签和领域文档时读 `setup-matt-pocock-skills`。选路有疑问时读 `ask-matt`。每次使用技能前读取当前安装版本的完整 `SKILL.md` 和该分支需要的引用，沿用原始技能名与方法。

- 用户主动发起 `grill`、`retro`、`handoff`。仓库内的 `grill` 走 `grill-with-docs`，通用讨论用 `grill-me`，两者使用 `grilling`。项目内可查证的问题先查，再记录用户决定。
- 证据不足用 `research`。需要运行验证的单个设计假设用 `prototype`。领域词义或边界冲突用 `domain-modeling`，按[领域文档约定](domain.md)记录。
- 大范围且关键决定相互依赖时用 `wayfinder` 推进决策。用 `improve-codebase-architecture` 识别架构问题，用 `codebase-design` 推敲模块接口与验证边界。
- 原因不明的缺陷或性能回退用 `diagnosing-bugs` 建立可重复反馈。外来工单用 `triage`，规格拆出的票沿现有依赖施工。
- 已有明确验收条件的单项实现用 `implement`。多票规格用 `to-spec` → `to-tickets` → `implement-spec`。逐票实施时按阻塞顺序在新上下文用 `implement`。
- 面向代理的约定用 `writing-for-agents`。需要外部知情人提供材料时用 `to-questionnaire`。只有人能执行的操作用 `wizard`。用户需要换一种解释时用 `wait-what`，需要分阶段学习时用 `teach`。

LingEuro 的自主协调层由用户授权。主协调者组织 `to-spec`、`to-tickets`、`implement-spec`、`implement`、`triage`、`wayfinder` 等步骤，并直接决定原版交由用户确认的常规工程事项。客户端限制隐式调用时，读原文后执行对应项目流程，交付时记录所采用的兼容方式与受限环节。技能名仍用于标识来源，实际调用按客户端能力报告。

## 规格、工单与集成

1. `to-spec` 汇总原始目标、可观察行为、关键决定、测试边界、范围外事项和必要约束。复杂规格按需请 Astra 独立核对遗漏、冲突、前提与可行性。主协调者核验证据并决定调整。
2. `to-tickets` 拆成可在新上下文单独实施和验收的 tracer-bullet tickets。记录真实阻塞，复杂依赖图独立核查。需要兼容迁移时按 expand–contract 排序，让各阶段都能验证。
3. `implement-spec` 读取规格与 task graph，创建 integration branch。可用探索子代理留下可复用的私有证据。对 ready frontier 中可独立完成的票派工，每名实施者使用独立分支和 worktree。行为按 `tdd` 验证。候选同步集成分支并重验后，由唯一 merger 串行合入，再释放后续工单。
4. `code-review` 固定同一基线与候选提交，分别在新上下文并行做 Standards 与 Spec 审查。Standards 读取适用项目规则和技能中的判断准则，优先采用自动检查证据。Spec 直接读取原始需求、完整规格与实际实现。两轴在出结论前各自工作。主协调者汇总，交给新实施者集中修复，重跑相关验证并复核最终提交。模型与派工见[多代理约定](multi-agent.md)。

跨阶段需要切换上下文时，参考 `ask-matt/PHASE-BOUNDARIES.md`。把原始目标和纠正、研究依据、规格、设计理由、提交、检查和审查通过可供下游读取的路径串起来。按需保存有明确读者和用途的记录。

## Git 与交付

- 按任务授权和仓库规则提交、推送、创建或更新 PR、合并与部署。只暂存本次范围。保留他人的工作和分支。遵守分支保护、审批与 CI。PR 正文用 `pr`，按跟踪器规则关联规格和工单，说明实际验证、影响与回滚风险。
- 机械冲突按原意处理。接口或验收契约的冲突由主协调者安排 Sol `high` 或 Astra `high` 判断，再验证集成结果。最终将检查证据对应到交付提交，更新已验收的工单和适用的 PR 状态。
- 清理临时 worktree 前核对归属、进程、分支与未提交内容，保全仍需要的私有材料。确认成果在本地分支、远端 PR、目标分支或部署中的实际状态。
- 开始时简述路线，重大调整时同步依据和影响。交付说明完成结果、关键决定、重要子代理的实际模型与角色、Git 位置、测试与独立审查结果，以及未验证或受限事项。

## 用户触发的复盘与交接

- `retro` 根据实际对话、Git、工单和检查结果，按技能分类提出环境改进。每项写明消费者、执行入口和验证方式。用户选定后接入工作流。
- `handoff` 记录目标与约束、当前技能或工单、资料指针、子代理状态、Git 与 PR、验证、阻塞及下一步。提供可直接复制的启动指令，新协调者先核实实际状态。
