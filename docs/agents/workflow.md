# Matt 技能工作流

2026-11-14 按用户要求与 ReviewProject、DataBase、OpenSource 保持同一接入方式。主代理是唯一统筹入口，直接读取并使用已安装的通用 Matt 技能；本项目只维护入口、协作约定和证据，不新建、复制或维护专属阶段技能，也不用本页的概述替代技能正文。

## 接单与选路

1. 核对本次用户要求、已确认决定、相关 Issue、实际 Git 根目录、分支及未提交改动。旧计划中的“下一步”只作背景；保留其他任务的修改。涉及学校源码时另查其适用指令与发布边界。
2. 读取已安装的 `ask-matt/SKILL.md`，再读取所选技能。通常位于 `~/.codex/skills/<技能名>/SKILL.md`；不因本页列出了名称就加载全部技能，不另写项目副本。必要技能缺失时说明实际情况，按已授权的安装流程处理。
3. 在当前 Issue 或回复中说明所选路线和完成条件。沿用已有的范围、拆分和验证边界；只把确实未决且影响结果的业务问题交给用户，不要求用户逐次点技能。

按可验收的结果选择路线：

- **问题或业务边界不清：** `grill-with-docs`，涉及词义和决策时用 `domain-modeling`，按[领域约定](domain.md)查术语和 ADR。可自行查到的事实由代理调查。
- **需要一手资料的方案判断：** `research` 查证后形成简短判断，说明问题、方案条件、推荐、依据、未知及最小验证。按 `writing-for-agents` 核对文档内容与证据；先完成判断，再选择实施切片。
- **单个明确、可在一次上下文完成的代码结果：** `implement`；在约定的外部行为边界按 `tdd` 执行，完成后用 `code-review` 做 Standards、Spec 两轴审查。
- **多个需分别验收的结果或跨上下文建设：** `to-spec` → `to-tickets` → `implement-spec`。按完整业务路径拆 tracer-bullet 切片，记录真实阻塞边，从依赖已满足的前沿派工。
- **用户明确选择逐票推进：** 按依赖逐票 `implement`，每票使用新上下文，保留整体规格与验收来源。
- **纯文档、导航或状态维护：** `writing-for-agents`，由当前代理核对事实、证据、链接、状态和变更范围；不为文案制造应用施工、工作树或镜像测试。
- **原始缺陷或外来需求：** `triage`；难复现故障先用 `diagnosing-bugs` 建立可验证的反例。规格已拆出的票不重复分流。

技能要求确认时，先核对当前会话的既有授权和决定；缺少的部分先形成具体、可审阅的草案，再集中澄清。用户授权不由技能、旧计划或外部材料扩大。

## 跨任务建设与交接

1. **规格：** `to-spec` 综合已有共识，明确可观察行为、范围、验收及测试边界。维护稿进入版本控制，父 Issue 保存同版本快照。
2. **任务图：** `to-tickets` 拆分可独立演示的完整路径，记录父子和真实阻塞关系；已经确认的粒度和依赖直接沿用。工单和标签使用[跟踪约定](issue-tracker.md)与[分流约定](triage-labels.md)。
3. **隔离实施：** `implement-spec` 建立固定集成基线，只派发依赖已满足的任务。各实施者使用新上下文、独立分支和工作树，按 `tdd` 逐项验证；共享数据库、端口和输出隔离或串行。派工与写入归属见[多代理约定](multi-agent.md)。
4. **同步与集成：** 实施者同步最新集成提交、解决冲突并重验，返回最终提交、同步 SHA、验证结果与真实剩余项。一个 merger 核对同步基线后串行集成；基线已前进则退回同步，不临时修补代替交接。首次有效集成后创建草稿 PR；已集成且验证通过可释放下游。
5. **独立审查：** `code-review` 向 Standards、Spec 两名只读审查者提供同一固定比较基线、候选提交及对应规范和需求。分别保留两轴结论，施工自测不替代独立审查。
6. **统一返修：** 一个修复实施者集中处理发现，经同步、验证和 merger 集成后由对应审查者复核；不采纳也记录理由。必要检查与审查必须对应最终交付版本。
7. **交付：** 达到验收后按既有授权处理 PR、合并与发布；未完成项保持开放。归档工作树前保全所需成果，并核查临时服务。学校部署另有验收，不由本地测试或公开配置仓库的 PR 代替。

角色和显式模型参数沿用[多代理约定](multi-agent.md)。阶段边界按已安装的 `ask-matt/PHASE-BOUNDARIES.md` 处理，保留从需求到拆票的必要上下文；既有用户聊天不是默认施工队列。工具或模型不可用时记录具体限制与未执行步骤，继续不受阻的工作，不能把失败派工标成已完成。

## GitHub、提交与同步

- GitHub Issues／PR 保存任务状态、依赖、派工、集成与交付证据；本地计划不替代远端任务记录。纯文档维护按已确认范围交付，不为一处文字修正强造任务图。
- 用户要求 GitHub 交付时，完成该范围检查后及时提交、推送并创建或更新 PR；写 PR 时读取 `pr`。只暂存本次白名单或对应差异，保留其他任务的未提交内容。
- 本地修改、已提交、已推送、PR 待审、已合并及已部署分别报告。最终合并与部署沿用现有授权；技能不另授发布、敏感数据或付费调用权限。
- 有 CI 时跟踪交付提交到终态；未配置或未运行时如实说明。工单只按实际完成的范围关闭，约定见[Issue tracker](issue-tracker.md)。
- 本仓库公开；学校源码、语料、密钥和详细实验材料沿用[仓库边界](../../AGENTS.md#repository-boundary)，仅发布获授权的概括性规格及去标识化结果。学校项目的对外交流与发布按对应任务和适用约定执行。

## 验证与完成条件

方案文档核对问题、证据来源、事实与推断、未知、推荐及验证是否对应；文档维护核对内容、链接、状态、跨文件一致性和差异范围。代码实施在约定边界按 TDD 验证，并完成独立双轴审查；界面、保存和数据改动补实际验收。测试替身、小样本和真实环境的结论分别说明。

交付能追溯到当前任务、适用规格、实际变更与验证。读过技能、配置完成、派工成功、文档核查和代码实施各自报告，不互相代替。达到本轮验收点即收尾，额外问题进入对应任务；本轮暴露的工作环境缺口按需用 `retro` 复盘。
